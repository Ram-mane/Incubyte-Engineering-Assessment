# Decision log

Every decision taken on this project and the reasoning behind it.

**Relationship to ADRs.** An ADR is for a decision that is expensive to reverse — one that would
cost a migration, a rewrite spanning more than one module, or a change to a published contract.
This log is for everything else: the smaller calls that shape the code and would otherwise survive
only in a chat transcript. Where a decision has an ADR, the log row points at it rather than
repeating it.

**Graduation rule.** If a row's *Why* cannot be said in one sentence, it is probably an ADR.
Write the ADR and reduce the row to a pointer.

**Status.** `Active` · `Superseded by Dnnn` · `Reversed` · `Probation` (will be deleted unless a
condition is met by a stated date)

IDs are chronological, so reading top to bottom shows how the design evolved. Grouping is by area,
so reading a section shows what governs one part of the system.

## Data model

| ID | Decision | Why | Status |
|---|---|---|---|
| D017 | Salary as an append-only effective-dated history | Most interesting questions about pay are historical. [ADR-0002a](adr/0002-temporal-salary-model.superseded.md) | **Superseded by D018** |
| D018 | Current salary on the employee, plus an append-only audit log | The customer confirmed current state is sufficient, removing every capability that justified the temporal model. The log was kept because an unlogged mutation of pay data is a trust problem costing one table to avoid. [ADR-0002](adr/0002-current-salary-with-audit-log.md) | Active |
| D019 | `Employee.changeSalaryTo()` returns the `SalaryRevision`; no setter on `currentSalary` | Makes the audit guarantee structural — there is no code path that changes pay without producing a record | Active |
| D020 | Application DB role has `INSERT`/`SELECT` only on `salary_revision` | The append-only guarantee is enforced by the database, not only by the repository | Active |
| D021 | PostgreSQL 16, not SQLite | `numeric`, `percentile_cont`, `pg_trgm`, partial and covering indexes, per-table grants — all four things the schema leans on. [ADR-0003](adr/0003-postgres-over-sqlite.md) | Active |
| D022 | Keyset pagination, no `OFFSET` | O(1) at any depth and stable under concurrent writes. [ADR-0004](adr/0004-keyset-pagination.md) | Active |
| D023 | Trigram GIN index for name search | `ILIKE '%x%'` cannot use a B-tree; at 10k a sequential scan is fast enough to hide the mistake | Active |
| D024 | Native SQL projections for the dashboard, JPA for writes | Four KPI cards in one round trip; no entity loaded to be summed in Java. [ADR-0005](adr/0005-native-sql-for-analytics.md) | Active |
| D025 | Single tenant, no speculative `tenant_id` | Partially-implemented isolation is worse than none. [ADR-0010](adr/0010-single-tenant.md) | Active |
| D090 | The employee schema is `V2`, not the `V1` the plan said, and every later planned migration number shifts by one | `V1__enable_required_extensions` is already applied on every environment, and Flyway validates the applied history by version and checksum: reusing or renaming `V1` fails startup on the deployed instance and on any developer database that has run it. Renumbering the plan is free; renumbering an applied migration is an outage. PLAN.md carries the note so 2.2 and 2.4 do not rediscover it | Active |
| D091 | No column in the schema has a `DEFAULT` and no table has a trigger — not for identity, not for time | Two rules that are one rule. Identity is application-assigned (D067, D079): a `gen_random_uuid()` default is a second source of identity that mints rows the domain never created, and the seed generator holds ten thousand employees with their ids before the first insert. Time is passed in, never consulted (D075): a `now()` default or a stamping trigger reintroduces the ambient clock one layer below the port, where no domain test can see it — the rule does not stop at the boundary just because the boundary is where the code stops. `EmployeeSchemaIT` asserts both against `pg_attrdef` and `pg_trigger`, so a later migration cannot add one quietly | Active |
| D092 | `Department` is an inline natural-key value object in `shared`, not a `DepartmentId` referencing a department table | Reverses D071. There is no department aggregate for an id to reference — nothing in the system does anything to a department — so `DepartmentId` was identity for an entity that does not exist. Two concrete costs: a `bigint` surrogate is a second identity policy beside the application-assigned UUIDs (D091), and every query that reads the dimension pays a join for it — 3.2's four-KPI single round trip joining a table it reads nothing from, the department breakdown joining to fetch the label it groups by, 2.6's filtered search joining before it can filter with its index on a surrogate the UI never sends, and 2.10 resolving names to ids for ten thousand rows. It is the same kind of thing as `JobTitle` and `SeniorityLevel`, which are already value objects in `shared` on the same grounds (D082), and the filter dropdown is `SELECT DISTINCT department` off the btree index. The cost accepted: renaming a department is an `UPDATE` across its employees rather than one row, which is a rare operation on ten thousand rows and needs no lookup table to make it cheap | Active |
| D094 | `SalaryRevision` still carries no identity in the domain, but its surrogate is a `uuid` the persistence adapter assigns, not a `BIGSERIAL` | Supersedes D079's second half; its first half is unchanged. A sequence default is a database-minted identity, which is precisely what D091 rules out, and an exception for one table would be two identity policies in one schema. Minting it in the adapter rather than in `changeSalaryTo` keeps the aggregate a pure function of its arguments, which was D079's actual reason for having no id in the domain. The key also earns its place: it is the keyset tiebreaker for the revision list, where `changed_at` alone is not a total order | Active |
| D095 | The migration creates the application's database role itself — `salary_app`, `NOLOGIN`, no password — and grants it least privilege per table | The append-only guarantee is only real if the role the application connects as cannot `UPDATE` or `DELETE` a revision (D020), and a grant is meaningless without a named grantee. Creating the role in the migration keeps the privilege model versioned and reviewable as SQL alongside the table it protects, and `NOLOGIN` with no password keeps credentials out of the repository — attaching a login is provisioning's job. It also makes the guarantee testable: Testcontainers connects as a superuser, which bypasses every grant, so the tests `SET ROLE salary_app` and are refused exactly as the deployed application would be. Cost: the migration user needs `CREATEROLE`, which has to hold on Neon and is verified at 2.14 | Active |
| D096 | A `CHECK` lands only where it mirrors an invariant the domain already enforces, traced to the method and the test — so `previous_amount > 0` was dropped | `new_amount > 0` mirrors `changeSalaryTo`'s positivity guard and `new_amount <> previous_amount` mirrors its no-op guard, both with named tests. `previous_amount > 0` mirrors nothing: `Money` holds zero and negative amounts by design, and `Employee`'s constructor requires only a non-null salary in the right currency. A database-only rule is one the domain will eventually violate, and it would have surfaced while seeding ten thousand rows rather than in a test. **Open gap this exposed:** I10 reads "an employee's salary must be > 0" but the constructor does not enforce it, so `new Employee(..., zero)` is legal in Java and refused by `employee_salary_is_positive`. Recorded, not fixed here | Active |
| D098 | The `change_reason` CHECK and the `ChangeReason` enum are asserted to be the same set, read from `pg_constraint` | The CHECK duplicates the enum by necessity (D078), and duplicated lists drift. Read back rather than restated, the drift fails the build; restated in the test, it would pass while an insert failed in production for a reason the domain considers valid | Active |
| D100 | Every migration that creates a table grants it in the same file, and `SchemaGrantsIT` fails the build for any table in `public` that does not grant the application role at least `SELECT` | The application now runs as a role with nothing it was not given (D097), so a forgotten `GRANT` is no longer an oversight but a runtime failure — one with no good moment to be found, since the migration succeeds, the context starts, and the first query in the screen that needs the table returns "permission denied". Table and privileges reviewed as one change; `flyway_schema_history` is the single named exclusion, and a second test asserts it really is ungranted so the exclusion cannot quietly hide a grant. Enumeration reads `pg_tables` and the check uses `has_table_privilege`, because `information_schema` lists only tables the current user already has privilege on and would have hidden precisely the tables being looked for. Privilege shape: `salary_revision` `SELECT, INSERT`; mutable tables `SELECT, INSERT, UPDATE`; `salary_band` and `exchange_rate` `SELECT`; no `DELETE` anywhere without a stated need | Active |
| D101 | Both `DataSource` beans are declared explicitly, because declaring one backs off Spring Boot's | `DataSourceAutoConfiguration` is `@ConditionalOnMissingBean(DataSource.class)`, and the condition is on the **type**, not on the qualifier. Adding a single `@FlywayDataSource` bean — the documented way to give Flyway a different pool — therefore removed the auto-configured application pool, and the whole application silently ran on the migration pool: no `connection-init-sql`, no `SET ROLE`, connected as the owner of `salary_revision`, which holds `DELETE` on it whatever is granted. Nothing logged a warning; the context started; the schema's grant-catalogue test still passed, because what a role *may* do is unchanged by whether anything connects as it. What caught it was the behavioural test going through the real `DataSource`: three of its six assertions failed. `current_user` named the cause in one line; the two refusal tests reported only that a statement they expected to fail had succeeded | Active |
| D102 | Commit `980491e`'s claim that the bean mistake "passed every test in the suite; only asserting `current_user` caught it" is **false** and is recorded rather than quietly dropped | Three of the six append-only tests failed on that run, including both refusal tests. The true and narrower statement is that the suite *as it existed before 2.3* passed — the grant-catalogue assertion cannot see whether anything connects as the role — and that `current_user` shortened the diagnosis rather than performing the detection. Second occurrence of the species D057 named: not wrong code, which a test catches, but a wrong claim about verification, which reads like evidence and is checkable only by rerunning what it describes. This one propagated — it was repeated back as the project's strongest guardrail evidence and was about to be used as talk material. Logged as [08-AI-WORKFLOW](08-AI-WORKFLOW.md) entry 8 | Active |
| D103 | The seed runs on its own pool, without `SET ROLE salary_app`, and `exchange_rate` and `salary_band` grant the application `SELECT` only | Granting `INSERT` at runtime to accommodate a provisioning task inverts the relationship: the runtime privilege would be shaped by the seeder rather than by what the application legitimately does, and "read-only reference data" would quietly mean "read-only except for the one job that writes it". Seeding is provisioning and is therefore **a deliberate privilege escalation**, visible as a `seed`-profile `DataSource` a reviewer can see and object to, rather than an unexplained `INSERT` grant nobody reads. The runtime grant keeps saying `SELECT` and meaning it | Active |
| D104 | `pg_stat_database` counters do not count statements, and the N+1 gate drafted on them was deleted rather than shipped | `xact_commit + tup_returned` counts transactions and rows, so the assertion would have held at any number of queries — a gate that reports success while measuring nothing, the species this project keeps finding. Worse, `CLAUDE.md` already promises that "integration tests count statements and fail if the count exceeds what the test declares", which no code in the repository does: **the working agreement is currently making a claim the code cannot back**. The harness is built for real at 2.6, where a filtered query with a join is the first place an N+1 can actually appear, and `CLAUDE.md` is corrected in that same commit | Active |
| D105 | The seed draws its salary spread as scaled integer percentage points, never a `double` multiplier | First written as `BigDecimal.valueOf(0.88 + random.nextDouble() * 0.24)` and corrected before it ran. "It is only test data" is exactly how a float gets near money: these ten thousand figures are what 3.2 sums into total payroll spend and what 3.7b pins a full-precision reference against, so a rounding artefact seeded here would surface as a dashboard number nobody could reconcile | Active |
| D106 | The directory's first query pages with `OFFSET`, contradicting ADR-0004 deliberately and with an end date | The vertical slice existed to prove the whole path — schema, query, port, endpoint, screen — against ten thousand real rows, and the pagination strategy is not what it was proving. `OFFSET` reads and discards every row it skips and can repeat or drop rows when data changes between pages, which is why the ADR rejected it. It ends at 2.6, where keyset arrives with the filters and search that settle the query's shape; that commit states whether ADR-0004 is thereby satisfied or superseded | **Superseded by D108** |
| D107 | The directory's sort tiebreaker is `id`, a UUID: the order it imposes is arbitrary but total | Keyset paging needs a total order or it duplicates and skips rows at page boundaries, and `family_name, given_name` is not one — two people share a name. `id` breaks the tie. Because it is a UUID rather than a sequence, the resulting order carries **no meaning at all**: it is not insertion order, not seniority, not anything. Recorded so that nobody later reads significance into the order two identically-named colleagues appear in, or "fixes" it into something that is no longer a total order | Active |
| D108 | Keyset paging lands at 2.6 and **ADR-0004 is satisfied, not superseded** | The ADR's decision was keyset over `OFFSET` with an opaque cursor, and that is what shipped: the cursor carries the whole sort key `(family_name, given_name, id)`, base64url-encoded so no client parses it, and the page is `(family_name, given_name, id) > (?, ?, ?)` — exactly the rows returned, stable while people are hired mid-paging. D106's temporary `OFFSET` ends here | Active |
| D109 | `totalApprox` is an exact filtered count on the first page and absent on every page after it — a deviation from ADR-0004's `pg_class.reltuples`, recorded rather than hidden | The ADR's objection is that `COUNT(*)` runs on **every** page, and that objection is honoured: it runs once per result set. A screen still has to say how large the result is, and `reltuples` cannot answer that for a *filtered* query — it estimates the whole table, so "Showing 1–50 of 10,000" would appear above a filter matching six people. At ten thousand rows one filtered count off the same indexes costs milliseconds. The field keeps the name `totalApprox` because that is the freedom being preserved: when the count starts to hurt it becomes an estimate and no client changes, since none was ever promised an exact number. Not an ADR — switching the count strategy is a one-line change in one adapter, which is the opposite of expensive to reverse | Active |
| D110 | The application's datasource must be the **direct** database endpoint, never a transaction pooler, and `DatabaseIdentityCheck` refuses to start when either pool has the wrong identity | Production died on `permission denied for table flyway_schema_history` — a message only a `salary_app` connection can produce, raised on the migration pool, which is configured never to be one. `FlywayConnectsAsTheOwnerIT` proves the configuration is right and that Flyway uses it, so the connection was contaminated rather than the config: a transaction pooler shares one server connection between clients, and `SET ROLE` (D097) is session state that travels with it. The timeline confirms it — the first deploy that could fail was the first one where a migrated database and an existing `salary_app` coexisted, and its diff was two test files. **The dangerous direction is the other one**: an application connection inheriting the owner's session would leave the `salary_revision` grant binding nothing, silently, which is the audit guarantee gone. So the check fails the boot instead, naming the pooler; `spring.flyway.init-sqls: RESET ROLE` is defence in depth for the first transaction. The alternative fix — granting `salary_app` rights on `flyway_schema_history` — was rejected: it would let a contaminated migration read the history and then fail on the next `CREATE TABLE` anyway, and it treats the symptom | Active |
| D111 | `ChangeSalary` and `GetSalaryRevisions` live in the `employee` module, not in a `compensation` module as 03-ARCHITECTURE drew it | The revision is what the `Employee` aggregate returns, so a separate module owning the use case would have to import `employee.domain` — precisely what architecture rule 4 forbids and what 1.12 made executable (D087). The alternative, moving `SalaryRevision` into `compensation`, would make `employee.domain` depend on it and create the cycle rule 6 forbids. The aggregate and the use case that mutates it belong together; `compensation` was a name for a capability, not a boundary the code can hold | Active |
| D112 | The pay-change endpoint returns 400 for every rejection the domain makes, not the 422 and 409 that 04-API-DESIGN specifies | Distinguishing "you sent nonsense" from "the domain refuses this" means the domain raising typed rejections rather than `IllegalArgumentException` with a message, and that is a domain change with its own tests. It belongs with the RFC 7807 mapping rather than smuggled into a use-case task. What is returned today is documented in `openapi.yaml` as what it is, so the contract does not claim a code it does not send. Terminated employees already return 422, because `IllegalStateException` is distinguishable | Active |
| D113 | Nothing outside `..domain..` may construct a `SalaryRevision`, enforced by ArchUnit | The audit guarantee is that a revision can only come from `changeSalaryTo`. An adapter able to build one from an employee's before-and-after state would let any code path that moves pay produce a plausible record, and the log would keep looking trustworthy while no longer being derived from the only method allowed to change pay. Proved by making the persistence adapter mint one and watching the rule name the method | Active |
| D114 | The first version of the authentication test was decorative, and the deliberate break is what revealed it | Asserting `401` on an unauthenticated request passed **with `permitAll` on the directory route**, because `@PreAuthorize` at the use case still refused an anonymous caller and that refusal is also a `401`. Status alone cannot distinguish "the chain rejected it" from "the chain let it through and the use case caught it" — which is the defence-in-depth working and the gate measuring nothing, simultaneously. The test now sends `?limit=abc`, which fails Spring's parameter binding in the controller before any use case is consulted: a closed chain answers `401`, an open one answers `400`. Third instance of the species this project keeps finding, and the first where the vacuous gate was a **security** test | Active |
| D115 | `changed_by` is the authenticated principal's id, taken from the token subject; the request body has no actor field at all | A caller able to name the author of a pay change can attribute one to a colleague, which makes the audit log evidence of nothing. The token's subject is the user's id rather than their email precisely so it can be the foreign key the revision stores, with no second lookup and no room for the two to disagree | Active |
| D116 | The JWT signing secret has no default and the application refuses to start without one of at least 32 characters | A fallback secret in a repository is a published secret, and this one signs the tokens that authorise payroll changes. Failing at startup is recoverable; running on a key an attacker can read from GitHub is not. The local profile carries an obviously-fake key for development, in the same file and for the same reason as the Docker Compose password | Active |
| D117 | `ix_employee_filter` was specified by 05-DATA-MODEL, created, measured, and **not shipped** | The planner never chose it. With the partial `ix_employee_rollup` available the filtered directory query prefers that one — narrower, already excluding non-`ACTIVE` rows, fewer index pages to walk — and the plans with and without the covering index are the same shape. An index nothing chooses is write cost with no read benefit, so the migration omits it and the data model is corrected rather than the index being shipped to make a document true. Both plans are in `docs/evidence/03-filtered-country-department.*`. Trigger to revisit: the hundred-thousand-row comparison at 3.12, where the arithmetic changes | Active |
| D118 | Three vacuous gates in one project is a pattern, and it has three distinct shapes worth naming | **(a) Vacuous by construction** — `pg_stat_database` counts transactions and rows, so an N+1 assertion built on it holds at any number of queries (D104). **(b) Vacuous by wrong counter** — `information_schema` lists only tables the current user already holds privilege on, so a gate hunting ungranted tables is blind to exactly the tables it exists to find (08-AI-WORKFLOW entry 9). **(c) Vacuous by masking** — a `401` on an unauthenticated request cannot distinguish a closed filter chain from an open one whose downstream `@PreAuthorize` refused the caller (D114); this one was hidden *by a correctly implemented second layer of defence*, which is the most dangerous shape because the system is genuinely safe while the test proving it is worthless. Two structural lessons: a gate is only known to work once a deliberate break makes it fail, and **every suite of refusals needs a control that succeeds** — without "a valid token returns 200", three 401 assertions pass equally well against a chain that rejects everything | Active |
| D119 | The session lives in `sessionStorage`, and a `401` navigates to the login screen with a reason rather than emptying the table | A token that authorises payroll changes should not outlive the tab it was issued to, and there is no refresh or revocation to lean on — which is why it is thirty minutes. The failure mode being avoided is specific: an expired session that shows an empty directory says "nobody works here", which is a statement about the company rather than about the request. The interceptor ends the session and routes to `/login?expired=true`, and the screen says the session expired | Active |
| D097 | The application's own connections run `SET ROLE salary_app`; the migration grants the login user membership in it | D020 was decorative without this. `salary_app` is `NOLOGIN`, so nothing connected as it: the application connected as the owner of `salary_revision`, which holds `DELETE` on it whatever the grants say. Membership plus `spring.datasource.hikari.connection-init-sql` makes the restriction apply to the running system, and 2.3 proves it through the application's own `DataSource` rather than by issuing `SET ROLE` itself — a test that grants itself the privileges it is testing is the vacuous-gate pattern in a new costume. Consequence: migrations need their own pool, because on a fresh database the role does not exist when the first connection opens and a migration running as `salary_app` could create nothing. Both pools are declared explicitly, because declaring one `DataSource` bean backs off Spring Boot's — which first left the entire application running on the migration pool, restriction applied to nothing | Active |

## Domain — Bands

| ID | Decision | Why | Status |
|---|---|---|---|
| D082 | `JobTitle` and `SeniorityLevel` moved from `employee/domain` to `shared` | `SalaryBand` needs both, and a module reaching into another module's domain breaks architecture rule 4. **Guard: a type moves to `shared` only when two or more modules genuinely consume it** — employee, band and analytics all group by these two. Without that test the kernel becomes the place everything goes | Active |
| D093 | D082's "two or more modules consume it" is read as **known consumers in committed scope**, not modules whose code exists today | Settled here so 3.3 does not re-argue it. `Department` joins `JobTitle` and `SeniorityLevel` in `shared` on identical standing: `analytics` groups its breakdown by all three, and that consumer is a day away in committed scope, which is the same basis on which the other two moved during 1.11. Reading the guard as "code that exists right now" would leave the third of four sibling filter dimensions in `employee/domain`, where `analytics` could only reach it by importing another module's domain — the precise thing architecture rule 4 forbids and 1.12 made executable (D087). The guard's purpose is to stop `shared` becoming the place everything goes, and a named consumer in committed scope is not everything | Active |
| D099 | `Employee`'s constructor enforces I1, reusing the same guard `changeSalaryTo` uses. Supersedes D096's decision to record the gap rather than close it | Recording it was the wrong call in this direction. A `CHECK` with no domain rule behind it produces rows the domain cannot write; a domain with no guard behind a `CHECK` produces objects the database cannot store, which is worse — the aggregate was constructible in a state that could never be persisted, so every unit test that built an `Employee` asserted against a looser object than the one that ships. The bite was timed: one seed-generator edge producing zero would have surfaced at 2.10 as a constraint violation mid-batch, not as a named constructor test. One `requirePositive` used by both entry points, so positive has one definition | Active |
| D083 | `SalaryBand` carries no `BandId` | Same principle as D079: found by the natural key of role, level and country, which `05-DATA-MODEL.md` already makes unique, and referenced by nothing. `BIGSERIAL` PK in the table, absent from the domain. The class diagram is corrected, as it was for `DepartmentId` (D071) | Active |
| D084 | Compa-ratio is held to 4 decimal places, `HALF_EVEN` | `1234567 / 1250000` recurs and must round somewhere: precise enough to sort a directory by, not so precise it implies accuracy the inputs lack | Active |
| D085 | All three band bounds must be greater than zero, not only the midpoint | Rejecting only the divisor would be a rule shaped by the implementation. A band with a zero minimum describes no range anyone could be paid within, so I10 now reads `0 < min ≤ mid ≤ max` | Active |
| D086 | Bounds are checked before the compa-ratio when classifying | Outside the range is a different statement from far from the midpoint: an employee under the minimum is `BELOW_MIN` whatever their ratio, and a band whose min sits below 0.9 of mid would otherwise report `LOW` for someone genuinely out of range | Active |

## Working method

| ID | Decision | Why | Status |
|---|---|---|---|
| D051 | Tests written and approved before implementation, every task | AI output is accepted because a test passes, never because the code looks plausible | Active |
| D052 | One commit per task; gate fixes get their own commit; doc changes describing the same behaviour fold in | The history is graded. A gate defect exists independently of the feature that exposed it; an invariant's doc line does not | Active |
| D053 | Gate fixes ordered *after* the code that makes them non-vacuous | A gate-fix-only commit would have failed on "no mutations found" — a red intermediate commit is worse than imperfect ordering | Active |
| D054 | `/prime` at the start of every session, `/wrap` at the end | `docs/STATUS.md` is the handoff; without it each session re-derives context | Active |
| D055 | `git log` wins where it disagrees with `STATUS.md` | The status file is hand-written and drifts; commits cannot | Active |
| D056 | Every rejected or corrected AI output recorded in [08-AI-WORKFLOW.md](08-AI-WORKFLOW.md) | The failures are more informative than the successes, and four of the first six became build rules rather than reminders | Active |
| D057 | An overstated verification claim logged as a distinct failure mode | Wrong code is caught by a test; a wrong claim about what was verified reads like evidence | Active |
| D063 | Validation stays in `Money`'s compact constructor; moving it to `Money.of()` to make it mutable-by-Pitest was rejected | `Money` is a record, so the canonical constructor is public: `new Money(rawBigDecimal, INR)` would bypass scale normalisation entirely. That trades an unmeasured invariant for a bypassable one — a correctness regression, and the reason is the bypass, not that the alternative merely suited a tool | Active |
| D064 | A mutation score is bounded by what the tool elects to mutate, and `07-TEST-STRATEGY.md` §5 says so | Pitest mutates no record compact constructor unless `-FRECORD` is set; even then it attributes no killer to coverage arising from a test class's static initialiser, and `Money`'s rounding policy has no mutable construct at all. The README quotes the number, so the number must carry its limits | Active |
| D065 | Pitest runs with `-FRECORD`, accepting uncovered mutations in record-generated methods | With the filter on, `ExchangeRate` generated zero mutations and the gate reported 100% having tested none of it. Off, the real constructor guards are mutated and killed and the score is 80% against a 70% threshold; the cost is junk survivors in `equals`/`hashCode`/`toString` | Active |
| D066 | `Money`'s rounding policy verified by a recorded manual probe rather than left unverified | No default mutator applies to `setScale(currency.scale(), HALF_EVEN)` — no conditional, no operator, no return value. `HALF_EVEN`→`HALF_UP` fails 3 of 4 rounding tests and `scale()+1` fails three nested classes; both are recorded in §5 and re-run when the policy changes | Active |
| D073 | PMD's `AvoidFieldNameMatchingMethodName` excluded, scoped with the reason in the ruleset | Accessors named after their field are this codebase's convention because that is what a record generates. PMD cannot see generated accessors, so the rule only ever fires on the one aggregate written by hand — renaming `Employee.id()` to `getId()` would make it the odd one out | Active |
| D074 | Pitest excludes `equals`, `hashCode` and `toString` from mutation | `-FRECORD` (D065) surfaces compact-constructor guards, which is the point, but it also surfaces every record's generated methods: eight new records added roughly forty mutations nobody writes tests for and the score fell to 58%, below the threshold. Excluding those three names keeps the guards mutated and the noise out; the cost is that `Employee`'s hand-written identity equality is excluded too, and is covered by two example tests instead | Active |
| D062 | Every numeric tolerance is derived and shown before it is accepted, never asserted | Three tolerances were specified and all three were wrong: `07-TEST-STRATEGY.md` §2's one minor unit, D050's "to the minor unit", and the 3.7b wording. The pattern is the finding — a tolerance is an arithmetic claim, and stating one without deriving it produces a test that passes by being kept small | Active |
